1. Visão geral da solução

O ProjetoCinema é uma aplicação Windows Forms (.NET 10) para gestão de um cinema: cadastro de gêneros, filmes, salas, sessões e venda de ingressos com seleção de assentos. A solução está dividida em cinco projetos, e essa divisão não é arbitrária — ela reproduz, camada por camada, exatamente a Layered Architecture descrita por Eric Evans e o padrão de separação defendido no artigo de DDD em .NET da DevMedia.

Projeto / PastaPapel na arquiteturaTema das referências ao qual corresponde
CinemaDomainDomain LayerDDD — Entidades, Modelo de Domínio, Camada de Domínio isolada (Evans, cap. 4 e 5; DevMedia)
CinemaRepositoryInfrastructure Layer / PersistênciaDDD — padrão Repository; ORM e Entity Framework Core (DbContext, Fluent API, Migrations)
CinemaServiceApplication / Service LayerDDD — Application Layer e Services; Tipos Genéricos avançados; validação de invariantes
CinemaAppPresentation Layer (UI)DDD — User Interface Layer, DTO/ViewModel; Injeção de Dependência (contêiner, ciclos de vida)
CinemaTestTestesVerificação das camadas + EF Core Migrations + composição manual do contêiner de DI
Dependências entre projetos (lidas dos arquivos .csproj):
CinemaApp → CinemaService → CinemaRepository → CinemaDomain
Observe que as flechas apontam todas para dentro: o CinemaDomain não referencia nenhum outro projeto. Esse é o critério prático do DDD de que o domínio não deve conhecer infraestrutura nem interface — o Domain Layer permanece puro.

2. Tema: Domain-Driven Design

Referências: DevMedia — “Introdução ao DDD em .NET” (devmedia.com.br/introducao-ao-ddd-em-net/32724); Eric Evans — Domain-Driven Design: Tackling Complexity in the Heart of Software (2003).

2.1 Linguagem Ubíqua (Ubiquitous Language) — Evans, cap. 2

Evans defende que o código fale o mesmo idioma dos especialistas do domínio. No projeto isso aparece de forma literal: todas as classes, propriedades e pastas usam os termos do negócio em português, como seriam ditos por um funcionário do cinema.

Termo do negócioOnde aparece no código
Filme, Gênero, Sala, SessãoCinemaDomain/Filme.cs, Genero.cs, Sala.cs, Sessao.cs
Ingresso, Item do IngressoCinemaDomain/Ingresso.cs, IngressoItem.cs
Classificação, Duração, Forma de PagamentoPropriedades Classificacao, Duracao, FormaPagamento
Cadastrar, Consultar, Selecionar assentosCinemaApp/Cadastros/, SelecaoAssentosForm.cs

2.2 Entidades (Entities) — Evans, cap. 5

Uma Entidade, em DDD, é o objeto definido pela sua identidade, e não pelos seus atributos. O projeto materializa esse conceito numa classe base abstrata:

// CinemaDomain/Base/BaseEntity.cs
public abstract class BaseEntity : IBaseEntity
{
    public int Id { get; set; }
}

Toda classe de domínio herda de BaseEntity (public class Filme : BaseEntity), ou seja, toda classe de domínio possui identidade própria — é modelada como Entidade. A interface vazia CinemaDomain/Base/IBaseEntity.cs funciona como marker interface: ela não traz comportamento, serve para restringir os genéricos das camadas superiores (ver §4) apenas a tipos que sejam efetivamente do domínio.

2.3 Agregados e Raiz de Agregado (Aggregates) — Evans, cap. 6

O agregado é um conjunto de objetos tratado como uma unidade de consistência, acessado por uma única raiz. O caso mais claro no projeto é o Ingresso:

// CinemaDomain/Ingresso.cs
public class Ingresso : BaseEntity
{
    public string Documento { get; set; }
    public DateTime DataCompra { get; set; }
    public List<IngressoItem> IngressoItens { get; set; }   // filhos do agregado
    public Sessao Sessao { get; set; }                       // referência a outro agregado
    public decimal ValorTotal { get; set; }
    public string FormaPagamento { get; set; }
}
  • Raiz: Ingresso. Os IngressoItem (os assentos comprados) só existem dentro de um ingresso e são acessados através dele.
  • Fronteira do agregado: confirmada em CinemaApp/Infra/ConfigureDI.cs, onde há repositório e serviço registrados para Ingresso mas não para IngressoItem. Isso é exatamente a regra de Evans: só a raiz do agregado tem repositório próprio.
  • Referência entre agregados por identidade: Ingresso aponta para Sessao, que é raiz de outro agregado, e não tenta controlar seu ciclo de vida.

O mesmo raciocínio vale para Filme → Genero e Sessao → Filme/Sala: agregados distintos que se referenciam.

2.4 Padrão Repository — Evans, cap. 6

Evans propõe o Repository como a abstração que entrega objetos de domínio à aplicação “como se fossem uma coleção em memória”, escondendo completamente a tecnologia de persistência. A interface do projeto é a tradução direta disso:

// CinemaRepository/Base/IBaseRepository.cs
public interface IBaseRepository<TypeEntity> where TypeEntity : IBaseEntity
{
    void Create(TypeEntity entity);
    TypeEntity ReadById(int id);
    IList<TypeEntity> ReadAll();
    void Update(TypeEntity entity);
    void Delete(int id);
}

Note que a interface não menciona EF Core, SQL ou PostgreSQL — ela devolve IList<TypeEntity>, uma coleção comum. Toda a tecnologia fica confinada na implementação CinemaRepository/Base/BaseRepository.cs. Consequência prática: trocar PostgreSQL por SQL Server, ou o EF Core por Dapper, não exige alterar uma linha de CinemaDomain nem de CinemaService.

2.5 Services (Camada de Aplicação) — Evans, cap. 4 e 5

Operações que não pertencem naturalmente a nenhuma entidade ficam em Services. Em CinemaService/Base/BaseService.cs, o serviço orquestra o caso de uso sem conter regra de negócio própria: ele valida, delega a persistência ao repositório e converte o resultado para o modelo de saída.

public TypeOutputModel Create<TypeInputModel, TypeOutputModel, TypeValidator>(TypeEntity entity) ...
{
    Validate(entity, Activator.CreateInstance<TypeValidator>());  // 1. invariantes
    _baseRepository.Create(entity);                                // 2. persistência
    return _mapper.Map<TypeOutputModel>(entity);                   // 3. tradução p/ fora
}

2.6 Invariantes do domínio (validação)

As regras que um objeto precisa sempre respeitar estão centralizadas em CinemaService/Validators/ (FluentValidation), um por entidade: FilmeValidator, GeneroValidator, SalaValidator, SessaoValidator, IngressoValidator, IngressoItemValidator. Exemplo em FilmeValidator.cs: nome obrigatório entre 5 e 50 caracteres, gênero não nulo, duração ≥ 1. Como a validação é disparada dentro do BaseService, nenhum caminho da aplicação consegue gravar um objeto inválido — nem a tela, nem os testes.

2.7 DTOs / ViewModels e a separação de camadas

A pasta CinemaApp/Models/ (FilmeViewModel, GeneroViewModel, SalaViewModel, SessaoViewModel, IngressoViewModel, IngressoItemViewModel) implementa o que o artigo da DevMedia chama de objetos de transporte entre a camada de aplicação e a de apresentação. Eles achatam o grafo de objetos para o que a tela precisa:

// CinemaApp/Models/FilmeViewModel.cs  — note GeneroId/GeneroNome em vez do objeto Genero
public class FilmeViewModel {
    public int Id; public string Nome; public string Classificacao;
    public int GeneroId; public string GeneroNome; public int Duracao;
}

A conversão Entidade ↔ ViewModel é configurada com AutoMapper em CinemaApp/Infra/ConfigureDI.cs, inclusive com projeções explícitas (ForMember(dest => dest.GeneroNome, opt => opt.MapFrom(src => src.Genero.Nome))). Resultado: o DataGridView da interface nunca enxerga uma entidade de domínio diretamente.

3. Tema: ORM e Entity Framework Core

Referências: Medium / We Are Developers — “Understanding ORM in C#/.NET: A Complete Guide”; entityframeworktutorial.net.

3.1 O problema que o ORM resolve neste projeto

O artigo do Medium define ORM como a ponte entre o modelo de objetos e o modelo relacional, eliminando o código ADO.NET repetitivo. No ProjetoCinema a existência dessa ponte é visível pelo que não existe: não há nenhuma linha de SqlCommand, DataReader ou SQL manual no código da aplicação. O SQL aparece apenas em CinemaTest/CinemaDB.sql (script auxiliar) e dentro das migrations geradas automaticamente.

Pacotes que fazem o ORM (lidos dos .csproj): Microsoft.EntityFrameworkCore 10.0.12 e o provider Npgsql.EntityFrameworkCore.PostgreSQL 10.0.3.

3.3 Fluent API — configuração do mapeamento objeto↔tabela

O tutorial de EF apresenta três formas de configurar o modelo: convenções, Data Annotations e Fluent API. O projeto escolheu deliberadamente a Fluent API com classes de configuração separadas (IEntityTypeConfiguration<T>), mantendo as entidades de domínio limpas de atributos de persistência — o que é também uma exigência do DDD (§2.2).

// CinemaRepository/Mapping/FilmeMap.cs
public class FilmeMap : IEntityTypeConfiguration<Filme>
{
    public void Configure(EntityTypeBuilder<Filme> builder)
    {
        builder.ToTable("Filme");                      // nome da tabela
        builder.HasKey(x => x.Id);                     // chave primária
        builder.Property(x => x.Nome)
               .IsRequired(true).HasMaxLength(50);     // NOT NULL / varchar(50)
        builder.Property(x => x.Classificacao)
               .IsRequired(false).HasMaxLength(20);
        builder.HasOne(x => x.Genero)                  // relacionamento 1:N
               .WithMany().IsRequired(true);
        builder.Property(x => x.Duracao)
               .HasDefaultValue(120);                  // valor padrão
    }
}

Há uma classe de mapeamento por entidade em CinemaRepository/Mapping/ (GeneroMap, FilmeMap, SalaMap, SessaoMap, IngressoMap, IngressoItemMap), todas registradas em OnModelCreating:

protected override void OnModelCreating(ModelBuilder modelBuilder) {
    modelBuilder.Entity<Filme>(new FilmeMap().Configure);
    modelBuilder.Entity<Sessao>(new SessaoMap().Configure);
    ...
}
Recurso da Fluent APIMétodo usado nos arquivos *Map.cs
Nome da tabelaToTable("Filme")
Chave primáriaHasKey(x => x.Id)
Obrigatoriedade / tamanhoIsRequired(), HasMaxLength()
Valor padrãoHasDefaultValue(120)
Relacionamento um-para-muitosHasOne(...).WithMany()

3.4 Change Tracking e estados da entidade

O ponto do tutorial de EF sobre rastreamento de mudanças está explícito no método Update de CinemaRepository/Base/BaseRepository.cs, que trata o caso clássico de entidade desanexada (vinda da tela) conflitando com uma instância já rastreada:

var localEntity = _myDBContext.Set<TypeEntity>().Local
                  .FirstOrDefault(e => e.Id == entity.Id);
if (localEntity is not null) {
    _myDBContext.Entry(localEntity).CurrentValues.SetValues(entity);
    _myDBContext.Entry(localEntity).State = EntityState.Modified;
} else {
    _myDBContext.Entry(entity).State = EntityState.Modified;
}
_myDBContext.SaveChanges();
  • .Local — consulta o change tracker sem ir ao banco;
  • CurrentValues.SetValues() — copia valores para a instância rastreada;
  • EntityState.Modified — marca a entidade como alterada;
  • SaveChanges() — traduz tudo para UPDATE em uma transação.

Os demais métodos ilustram o ciclo completo: Add (Added), Remove (Deleted) e Set<T>().AsQueryable() para leitura via LINQ.

4. Tema: Tipos Genéricos em C#

Referência: NextWave Education — “Trabalhando com tipos genéricos em C#”.

Este é, provavelmente, o tema mais fortemente explorado no projeto: a genericidade é o que evita escrever cinco repositórios e cinco serviços praticamente idênticos.

4.1 Classe genérica + restrição de tipo (where)

// CinemaRepository/Base/BaseRepository.cs
public class BaseRepository<TypeEntity> : IBaseRepository<TypeEntity>
    where TypeEntity : BaseEntity        // restrição de classe base

A restrição where TypeEntity : BaseEntity é o que torna o código possível: sem ela, a linha dbContext.ToList().Find(x => x.Id == id) não compilaria, porque o compilador não saberia que TypeEntity tem a propriedade Id. É o exemplo didático perfeito de por que restrições existem.

Note a diferença sutil e intencional entre interface e implementação:

DeclaraçãoRestrição
IBaseRepository<TypeEntity>where TypeEntity : IBaseEntity (contrato mais permissivo)
BaseRepository<TypeEntity>where TypeEntity : BaseEntity (precisa do Id concreto)
IBaseService<TypeEntity> / BaseService<TypeEntity>where TypeEntity : IBaseEntity

4.2 Métodos genéricos com múltiplos parâmetros de tipo

O caso mais avançado do projeto está em CinemaService/Base/IBaseService.cs: um método genérico, dentro de uma classe genérica, com três parâmetros de tipo e uma restrição diferente para cada um.

TypeOutputModel Create<TypeInputModel, TypeOutputModel, TypeValidator>(TypeEntity entity)
    where TypeInputModel  : class
    where TypeOutputModel : class
    where TypeValidator   : AbstractValidator<TypeEntity>;
  • TypeInputModel / TypeOutputModel — restrição class (tipo de referência): permitem que o mesmo serviço aceite e devolva DTOs diferentes conforme o caso de uso.
  • TypeValidator — restrição de tipo genérico aberto aninhado (AbstractValidator<TypeEntity>): o compilador garante, em tempo de compilação, que só se pode passar um validador da entidade correta. Tentar _filmeService.Create<..., GeneroValidator>(filme) nem compila.

Uso real em CinemaApp/Cadastros/CadastroFilme.cs:

_filmeService.Create<Filme, Filme, FilmeValidator>(filme);
_filmeService.Update<Filme, Filme, FilmeValidator>(filme);
var filme = _filmeService.ReadById<Filme>(id);
_generoService.ReadAll<GeneroViewModel>().ToList();

A última linha mostra o ganho concreto da parametrização da saída: o mesmo método genérico devolve a entidade (Filme) quando a tela precisa editar, e a ViewModel (GeneroViewModel) quando precisa popular um ComboBox.

4.3 Instanciação dinâmica de um tipo genérico

// CinemaService/Base/BaseService.cs
Validate(entity, Activator.CreateInstance<TypeValidator>());

Activator.CreateInstance<T>() cria o validador em tempo de execução a partir do parâmetro de tipo — a alternativa a isso seria a restrição where TypeValidator : new(), mencionada no material de genéricos.

4.5 Herança + polimorfismo como complemento aos genéricos

Onde o genérico não resolve (o layout de cada tela é diferente), o projeto usa herança com métodos virtuais em CinemaApp/Base/CadastroBase.cs: CarregaGrid(), Salvar(), Novo(), Editar(), Deletar(int) e CarregarRegistro(DataGridViewRow) são protected virtual e sobrescritos em cada Cadastro*. É o padrão Template Method: a classe base concentra o fluxo comum (confirmação de exclusão, limpeza de campos, troca de aba) e delega o específico às subclasses.

5. Tema: Injeção de Dependência em .NET

Referências: Microsoft Learn — “Injeção de dependência em .NET” (dotnet/core/extensions/dependency-injection/overview); Adriano Programador (Medium) — “.NET: Injeção de Dependência”.

5.1 O contêiner e sua composição

Toda a configuração de DI está concentrada em um único arquivo, CinemaApp/Infra/ConfigureDI.cs, que é a Composition Root da aplicação — o único lugar que conhece as implementações concretas. É chamado na primeira linha útil de CinemaApp/Program.cs:

static void Main() {
    ConfigureDI.Configure();              // monta o contêiner
    ApplicationConfiguration.Initialize();
    Application.Run(new FormPrincipal());
}
// ConfigureDI.cs — padrão descrito na documentação da Microsoft
Services = new ServiceCollection();       // 1. coleção de descritores
Services.AddDbContext<MyDBContext>(o => o.UseNpgsql(strCon));
Services.AddScoped<IBaseRepository<Filme>, BaseRepository<Filme>>();
...
ServiceProvider = Services.BuildServiceProvider();   // 2. provider

Pacote: Microsoft.Extensions.DependencyInjection 10.0.13. Vale registrar que o uso é notável por ser num Windows Forms: a infraestrutura de DI do .NET, normalmente associada a ASP.NET Core, é aqui montada manualmente em uma aplicação desktop.

5.2 Ciclos de vida (service lifetimes)

Os três tempos de vida descritos pela Microsoft estão todos presentes, e cada escolha tem justificativa:

LifetimeRegistros no projetoPor quê
ScopedIBaseRepository<T> e IBaseService<T> de Genero, Filme, Sala, Sessao, Ingresso; o MyDBContext via AddDbContextAcompanham o tempo de vida do DbContext, que não é thread-safe nem deve viver por toda a aplicação
SingletonServices.AddSingleton(mapperConfig.CreateMapper())O IMapper do AutoMapper é imutável e caro de construir — uma instância basta
TransientAddTransient<CadastroGenero>(), CadastroFilme, CadastroSala, CadastroSessao, CadastroIngressoCada abertura de formulário precisa de uma instância nova (um Form fechado não pode ser reaberto)

5.3 Injeção por construtor

Nenhuma classe do projeto instancia suas próprias dependências com new; todas as recebem pelo construtor, que é a forma recomendada na documentação da Microsoft.

// CinemaApp/Cadastros/CadastroFilme.cs
private readonly IBaseService<Filme> _filmeService;
private readonly IBaseService<Genero> _generoService;

public CadastroFilme(IBaseService<Filme> filmeService, IBaseService<Genero> generoService)
{
    _filmeService = filmeService;
    _generoService = generoService;
    InitializeComponent();
}

A cadeia completa que o contêiner resolve automaticamente ao pedir um CadastroFilme:

CadastroFilme ← IBaseService<Filme> ← IBaseRepository<Filme> + IMapper ← MyDBContext ← DbContextOptions (connection string de CinemaApp/Config/ConfigDB.txt)

Os campos readonly e a dependência declarada como interface (IBaseService<T>, não BaseService<T>) são exatamente o que o artigo do Medium chama de inversão de dependência: a tela depende de um contrato, não de uma implementação.

5.4 Resolução de serviços e o Service Locator

O ServiceProvider exposto estaticamente por ConfigureDI é usado pelo CinemaApp/FormPrincipal.cs para obter os formulários do menu (GetService<CadastroFilme>()). Esse é o ponto de entrada necessário em Windows Forms, onde não existe um host que resolva a raiz automaticamente — vale notar, como observação crítica, que resolver serviços pelo provider é o padrão Service Locator, aceitável na Composition Root mas que, se espalhado pelo código, anularia o benefício da injeção por construtor.

5.5 DI nos testes

Em CinemaTest/TestCinemaService.cs o contêiner é remontado de forma isolada, com connection string própria e apenas os registros necessários:

services = new ServiceCollection();
services.AddDbContext<MyDBContext>(o => o.UseNpgsql(conStr));
services.AddScoped<IBaseRepository<Genero>, BaseRepository<Genero>>();
services.AddScoped<IBaseService<Genero>, BaseService<Genero>>();
services.AddSingleton(new MapperConfiguration(...).CreateMapper());
var generoService = serviceProvider.GetService<IBaseService<Genero>>();

Isso evidencia o principal benefício prático apontado nas duas referências de DI: como as camadas dependem de interfaces, é possível compor um grafo de objetos diferente para teste sem alterar o código de produção. Os arquivos TestCinemaDomain.cs e TestCinemaRepository.cs fazem o mesmo para as camadas inferiores.
